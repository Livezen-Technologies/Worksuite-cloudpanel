# Docker Manager Portal — Software Requirements Specification
 ·  · Version 1.0
## 1. Introduction
### 1.1 Purpose
This document specifies the requirements for the Docker Manager Portal: a self-hosted platform that lets operators manage Docker on many VPS and dedicated servers, and lets customers host Docker apps and connect their own domains. It is the reference for design, development, QA and acceptance of release 1.0.
### 1.2 Scope
The product has two web front ends on one control plane:
Admin portal — for platform operators: servers, agents, containers, Compose stacks, images, networks, storage, domains and SSL, databases, backups, monitoring, logs and terminal, automation, users and settings.
Customer (user) panel — for tenants: host a Docker app in four steps, connect a domain with automatic HTTPS, manage apps, restore backups, see billing and manage their account.
A Go agent on every managed server executes Docker operations. Kubernetes and Swarm backends, high-availability control plane and automated scaling are out of scope for 1.0 (see section 9).
### 1.3 Definitions
Term
 | Meaning
 |

 | Central API, scheduler, job queue and database that store desired state
 |

## 2. Overall description
### 2.1 Product perspective
The portal is a centralised, agent-based control plane. PostgreSQL holds desired configuration; agents on each server execute typed, policy-checked Docker operations and report actual state back. Applications keep running if the control plane is unavailable.

### 2.3 Operating environment
Managed servers: Ubuntu 22.04/24.04, Debian 12, Rocky Linux 9, AlmaLinux 9 with Docker Engine 24+.
Browsers: last two versions of Chrome, Edge, Firefox, Safari; layouts work from 360 px to desktop.
Control plane: one management VPS for small installs; separate management, database, observability, worker and storage nodes for large installs.
### 2.4 Design constraints
The Docker daemon TCP socket shall never be exposed publicly; agents connect outbound on 443 only.
Untrusted builds run on isolated worker nodes, never on the control plane or production hosts.
Standard Compose targets one host; multi-server placement is done by the portal scheduler, not by Compose.
Rebooting, resizing or reinstalling a server requires a provider API; Docker access alone cannot do it.
S3-compatible storage is used for backups and object data, not as a POSIX volume.
### 2.5 Assumptions and dependencies
Customers control DNS for the domains they connect.
Let's Encrypt is reachable from each ingress server; DNS-01 needs a DNS provider API token.
A payment provider (e.g. Stripe) is available for the customer billing module.
Provider integrations (Hetzner, DigitalOcean, Vultr, Linode, AWS, Proxmox) depend on account API permissions.

### 5.2 Host a Docker app (UHOST)

Source — Docker image (Docker Hub, GHCR, private with credentials), Git repository (built from its Dockerfile on an isolated runner), Compose file (pasted or uploaded), or a one-click template (WordPress, n8n, Ghost, PostgreSQL, Redis, Uptime Kuma).

Size — Small (0.5 vCPU, 512 MB, 5 GB), Standard (1 vCPU, 1 GB, 10 GB), Pro (2 vCPU, 4 GB, 40 GB); prices from the plan catalogue.
Deploy — live progress: pull image, start container, health check, certificate issued, live; then the free address <app>.<platform-domain>.

## 6. External interfaces
### 6.1 User interface
Two shells on one design system (Tailwind CSS v4): the admin portal with a 16-item sidebar and the customer panel with a 6-item sidebar.
Light and dark themes, one accent colour, Inter for text and JetBrains Mono for code, IDs and addresses.
Shared components: stat tiles, status badges, data tables, cards, side drawers, confirm dialogs, toasts, tabs, step wizards, command palette.
Responsive from 360 px: the sidebar collapses to a drawer, toolbars wrap, wide tables scroll inside their card.
Status is never shown by colour alone: every badge carries a word.

Long-running mutations return 202 with a job ID.
Mutations accept an Idempotency-Key header.
Errors use one structured format: code, message, field errors, request ID.
Rate limits apply per token and per IP.
### 6.3 Real-time channels
Authenticated WebSocket channels for metrics, job progress, live logs and terminal sessions. Each session is authorised per resource, expires, and writes audit events on open and close.
### 6.4 Agent protocol
Outbound mTLS on port 443; the certificate is bound to one server and organisation and rotated automatically.
Commands are typed, versioned and signed, with operation IDs to prevent duplicate execution.
Every command is checked against a local policy; there is no generic remote shell.
Heartbeat every 15–30 s; reconnect with exponential backoff.
Agent upgrades are signed, staged, health-checked and reversible.

### 8.3 Reliability and recovery
Agents reconnect automatically with exponential backoff.
Interrupted jobs resume or roll back; no job runs twice for one operation ID.
Recovery point and recovery time objectives are set per service tier and tested.
Control-plane database backups are stored off-host.
### 8.4 Usability and accessibility
WCAG 2.2 AA: 4.5:1 text contrast, keyboard access to every action, visible focus, labelled icon buttons.
Touch targets at least 44 px in the customer panel.
Customer copy avoids Docker jargon; errors say what happened and what to do next.
### 8.5 Portability and maintainability
Agent runs on x86_64 and ARM64.
The orchestration layer is modular so Swarm or Kubernetes backends can be added without changing the portals.
The API is versioned; breaking changes go to a new version.
